# Why&What

**Кулаков Никита Сергеевич, Web-13**  
Учебный сайт вопросов и ответов на Django. Текущий этап — ДЗ3: модели, PostgreSQL и отображение данных из БД.

[VK education](https://education.vk.company/profile/nik.kulakov/)

Списки вопросов и страница вопроса работают на данных PostgreSQL. Пользовательская авторизация, сохранение форм и обработка кнопок голосования пока не реализованы. Пользователь в шапке сайта демонстрационный. Вход в Django Admin работает через суперпользователя.

## Что сделано

- Модели вопросов, ответов, тегов, профиля пользователя и голосов с ограничениями на повторные голоса и связи вопроса с тегом.
- Выборки новых и лучших вопросов, вопросов по тегу и ответов, расчёт рейтингов в менеджерах моделей.
- Пагинация вопросов и ответов по 4 записи, обработка 404 и пустых списков.
- Админка на русском языке с поиском, фильтрами, профилем внутри пользователя и ответами внутри вопроса.
- Django Debug Toolbar только при `DEBUG=True`, предзагрузка тегов карточек через `prefetch_related`.
- Отображение даты и времени создания вопросов и ответов по Москве (`Europe/Moscow`).

- Команда `fill_db` для массового наполнения БД тестовыми данными с Faker и пакетной вставкой через `bulk_create`.

При первом запуске БД пустая. Для наполнения используйте `fill_db` по инструкции ниже или создайте записи вручную в админке.

## Настройка окружения

Проект запускается через Docker Compose. Отдельно устанавливать Python и PostgreSQL не нужно.

Все команды ниже начинайте выполнять из корня проекта — папки, где находятся `README.md` и `docker-compose.yaml`.

Настройки хранятся в файлах:

- `.env.docker` — для запуска в Docker.
- `.env.example` — пример без действующих секретов, хранится в Git.

Скопируйте `.env.example` в `.env.docker`:

Linux / macOS / WSL:

```bash
cp .env.example .env.docker
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env.docker
```

Откройте созданный файл в редакторе и заполните значения:

| Переменная | Назначение |
| --- | --- |
| `SECRET_KEY` | Собственный случайный ключ Django вместо заглушки |
| `DEBUG` | `True` для учебного запуска и Debug Toolbar |
| `POSTGRES_DB` | Имя базы данных |
| `POSTGRES_USER` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | Собственный пароль PostgreSQL вместо заглушки |
| `DB_HOST` | `db` — имя сервиса PostgreSQL в Docker |
| `DB_PORT` | `5432` при текущей конфигурации Compose |

В примере указан `DB_HOST=127.0.0.1`. В `.env.docker` замените его на `DB_HOST=db`.

Ключ можно сгенерировать командой:

```bash
docker run --rm python:3.14-slim python -c "import secrets; print(secrets.token_hex(32))"
```

Файл `.env.docker` исключён из Git. Параметры `POSTGRES_*` инициализируют PostgreSQL при первом создании volume: изменение файла окружения не меняет пароль или имя уже существующей БД.

## Запуск в Docker

Нужен установленный и запущенный Docker. После настройки `.env.docker` выполните:

```bash
docker compose up -d --build
docker compose exec web sh
```

Теперь вы внутри контейнера. Создайте таблицы и администратора обычными командами Django:

```sh
python manage.py migrate
python manage.py createsuperuser
exit
```

`migrate` создаёт таблицы, `createsuperuser` — администратора, `exit` возвращает в терминал компьютера. Сайт после выхода продолжает работать. Если БД ещё запускается и `migrate` выдаёт ошибку подключения, подождите несколько секунд и повторите команду внутри контейнера.

Откройте [сайт](http://localhost:8000/) или [админку](http://localhost:8000/admin/).

В следующий раз достаточно `docker compose up -d`. Для новых миграций снова войдите через `docker compose exec web sh` и выполните `python manage.py migrate`. Администратора повторно создавать не нужно. После изменения зависимостей используйте `docker compose up -d --build`.

Остановка: `docker compose down`. Данные БД и загруженные файлы сохранятся. Логи: `docker compose logs -f web`.

## Наполнение БД тестовыми данными

Команда `fill_db` создаёт пользователей, их профили, теги, вопросы, связи вопросов с тегами, ответы и голоса со значениями `+1` и `-1`. Имена и тексты генерируются библиотекой Faker. Записи сохраняются через `bulk_create` пачками до 1000 объектов; ответы и голоса также подготавливаются порциями.

Перед запуском должны быть запущены контейнеры и применены миграции, как описано в разделе «Запуск в Docker».

Для небольшой проверки из корня проекта выполните:

```bash
docker compose exec web python manage.py fill_db 10
```

Число после `fill_db` — обязательный целочисленный коэффициент `ratio`. Минимальное значение — `2`: при `ratio=1` невозможно создать требуемое количество уникальных голосов. Общий вид команды внутри контейнера:

```sh
python manage.py fill_db <ratio>
```

За один успешный запуск команда добавляет:

| Записи | Количество | При `ratio=10` | При `ratio=10000` |
| --- | --- | --- | --- |
| Пользователи | `ratio` | 10 | 10 000 |
| Профили пользователей | `ratio` | 10 | 10 000 |
| Теги | `ratio` | 10 | 10 000 |
| Вопросы | `ratio * 10` | 100 | 100 000 |
| Связи вопросов с тегами | `ratio * 10 * min(3, ratio)` | 300 | 300 000 |
| Ответы | `ratio * 100` | 1 000 | 1 000 000 |
| Голоса за вопросы и ответы суммарно | `ratio * 200` | 2 000 | 2 000 000 |

Каждый новый вопрос получает до трёх разных тегов. За каждый вопрос голосуют до десяти разных пользователей. Оставшееся до `ratio * 200` количество голосов создаётся за ответы текущего запуска. При `ratio >= 10` голоса распределяются поровну между вопросами и ответами. Не каждый ответ обязательно получает голоса. Рейтинг — сумма значений голосов, поэтому он может быть положительным, отрицательным или нулевым.

Для объёма, указанного в ДЗ, используется команда:

```bash
docker compose exec web python manage.py fill_db 10000
```

Это длительное наполнение миллионами записей; сначала проверьте работу на `ratio=10`.

Каждый запуск **добавляет новые данные**, сохраняя существующие записи. Например, два успешных запуска с `ratio=10` добавят суммарно 20 пользователей и 200 вопросов. Числа в таблице не включают ранее созданные записи, в том числе суперпользователя.

Тестовые пользователи имеют логины с префиксом `test_` и не могут входить на сайт: им задаётся непригодный для входа пароль через `set_unusable_password()`. Для админки используйте суперпользователя, созданного командой `createsuperuser`.

## Проверка

После запуска открыть [http://localhost:8000/](http://localhost:8000/).

| Адрес | Содержимое |
| --- | --- |
| `/` | Новые вопросы |
| `/hot/` | Вопросы по убыванию рейтинга |
| `/tag/<имя_тега>/` | Вопросы существующего тега |
| `/question/<id>/` | Вопрос и его ответы |
| `/admin/` | Админка, вход через созданного суперпользователя |
| `/ask/`, `/login/`, `/signup/`, `/profile/` | Интерфейсы форм |

Использовать существующие ID вопросов и имена тегов из БД. Для пагинации добавить `?page=2`; вторая страница появляется, когда записей больше четырёх. Отсутствующие вопросы и теги возвращают 404, существующий тег без вопросов — сообщение о пустом списке.

При `DEBUG=True` на HTML-страницах появляется Django Debug Toolbar. Панель SQL показывает запросы, их время и место вызова. Для списка вопросов основные операции — подсчёт для пагинации, загрузка вопросов с рейтингом и количеством ответов, общая загрузка тегов. Запросы пользователя и сессии могут добавляться отдельно.

Признак N+1 — отдельные похожие запросы для каждой карточки, отличающиеся ID объекта. Теги должны загружаться одним запросом для набора ID вопросов. При `DEBUG=False` приложение, middleware и маршруты Debug Toolbar не подключаются.
